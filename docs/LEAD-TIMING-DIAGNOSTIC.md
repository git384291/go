# 접수 응답 시간 진단 (P2: 연락처 존재 여부 추론) — 미해결 유지

판정: **해결 아님.** 현재 개발모드 로컬 HTTP 조건에서는 존재 여부 구분 근거가 입증되지 않음. 로컬 운영 빌드 조건에서는 제3자 입력 기준 구분 근거가 입증되지 않았고, 원본 내용을 아는 경우에만 약한 신호가 보였다.
운영 인터넷 환경 측정이 아니다. 배포 대상 DB의 마이그레이션 상태는 미검증이다.

## 측정 환경 (CI 러너, 127.0.0.1)
- 개발모드(BF30): Next E2E 시험 전용 앱 `next dev`.
- 로컬 운영 빌드(BF31, 1회): 같은 fixture를 `next build` + `next start`로 실행. 런타임 `NODE_ENV=test`는 기존 로컬 봇 확인 대체 경로(TURNSTILE_VERIFY_URL_TEST, development/test에서만 허용)를 쓰기 위함 — 운영 코드 변경·새 우회 경로 없음.
- 공통: 폐기 PostgreSQL(실고객·운영 DB 없음), 가짜 봇 확인 서버(로컬 HTTP), 고지 확정 fixture. 실제 `/api/leads` 요청→응답 전체(고지 확인·암호화·서명·트랜잭션·레이트리밋 포함). 요청마다 다른 시험 IP(기존 E2E 격리 방식).

## 표본·평가
- 예열 20회 버림, 기준 연락처 40개 생성 후 신규·같은 내용 재접수·변경 재접수 각 100회 무작위 순서.
- 요청마다 DB 처리 결과(리드·변경 요청·재문의 증가)를 확인 — 300건 모두 의도와 같았다(BF30·BF31 PASS 조건은 이것뿐, 시간 값은 합격 조건 아님).
- 범주마다 짝수 번째 50건 = 기준(보정) 표본, 홀수 번째 50건 = 평가 표본. 평가 표본의 균형 정확도·오분류를 보고(무작위 = 0.50). 단순 정확도는 다수 범주 기준과 함께 적는다.
- 제3자 입력 = 원본 내용을 몰라도 보낼 수 있는 요청(기존 번호 + 임의 내용 → 변경 요청 경로). 같은 내용 재접수는 원본 내용을 알아야 가능(별도 표시).

- 평가 표본 100건의 균형 정확도 오차 범위는 대략 ±0.10. 개발모드 값은 실행마다 0.49~0.62로 흔들려 일관된 방향이 없다.
- 로컬 운영 빌드: 제3자 입력 0.58은 오차 범위 경계(입증 안 됨). 원본 내용을 아는 경우 0.66은 약한 신호(같은 내용 재접수가 약 0.6ms 빠름). 다만 원본 내용을 아는 사람은 이미 신청 존재를 아는 경우가 대부분이다.
- e5b4886의 운영 빌드 측정은 무효(시험 스크립트 버그: 요청 키가 앞 진단과 겹쳐 서버가 재전송으로 처리, 저장 없이 202). 663dc81에서 실행별 키 접두어로 고친 뒤의 1회가 첫 유효 측정이다.

## 이전 71~76% 수치의 방법론 한계
- HTTP가 아니라 DB 함수만 psql로 직접 호출한 시간(앱·네트워크·암호화 제외).
- 기준을 정한 표본과 평가한 표본이 같은 300건(표본 내 평가) → 낙관적.
- 단순 정확도. "신규 vs 기존 전체"(300 대 600)의 71%는 다수 범주 기준 66.7% 대비 약 4%p 개선에 불과.

## 남은 위험 (P2 유지)
- 운영 인터넷·실제 봇 확인(Cloudflare)·운영 DB 부하 조건은 측정하지 않음.
- 완화 요소(실측 아님): IP당 시간 10건 제한, 봇 확인, 네트워크 지연 변동, 같은 번호는 한 번 조회하면 리드가 생겨 '새 번호' 상태로 반복 측정 불가.
- 인위적 지연은 추가하지 않았다(PM 지시).
