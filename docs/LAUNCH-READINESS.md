## 0. 오늘 상담·접수 경로 — 최신 현황과 최소 선행조건 (PM 6907580567, 기준 `11008ad`)

**결론:** 지금은 두 경로 모두 **고객 공개 불가**다.
- CI 통과나 가상 신청은 실접수·출시 완료로 세지 않는다.
- 이 절은 정리만 담는다. 코드·스키마·환경·권한·실계정·스위치는 바꾸지 않았다.

**표기 범례** — 각 항목을 다음 4단계로 따로 기록한다.
- 단계: **코드** = 코드 존재 / **가상** = 가상·로컬 검증 / **실연결** = 실연결 검증 / **공개** = 고객 공개

- **해결 주체:** 사용자 = 외부 계정·본인인증·계약 등 사용자만 할 수 있는 일, Claude = 코드로 해결할 일, PM = 결정·승인

### 0-2. 경로 2 — FIDEON 자체 최소 접수 (이름·휴대폰·희망 시간)

2. 사용자 외부 작업: 도메인(구매·유료 자원 비용은 광고 예산 승인에 포함되지 않으며 PM 결정), Supabase 대표 계정·TOTP(기존 fideon-dev 사용), Cloudflare Turnstile 키. Claude는 키·계정을 만들지 않는다.

5. ① 처리방침 확정·게시 → ⑬ 스위치는 대표가 마지막에 연다. 고객 공개 전에 PM 최종 검수를 거친다.

**웹앱 검수 기준(공개 전 모두 실연결로 확인)**
- 접수 성공과 저장 실패를 정확히 구분해 안내한다.
- 관리자 접근을 통제한다: 미인증 401, 권한 없음 403, TOTP 필수.

**오늘 공개 가능성:** ②·③·④·⑧·⑪이 외부 계정·인증·도메인에 걸려 있어, **개발만으로 오늘 열 수 없다.**

- 예산: 승인된 상한 유지

### 0-3. 상담 폼 계약과 한계 (PM 6907697718 A·B)
**코드 위치**
- `src/components/consultSubmit.ts`: 필드 검증, 요청 키 계약, 응답 분류
- `src/components/ConsultForm.tsx`: 폼
- `src/components/TurnstileWidget.tsx`: 봇 방지 위젯
- `src/server/leads/turnstile.ts`, `src/app/api/leads/route.ts`: 서버 예외 경계

**폼 동작**
- **요청 키**
  - 직전 시도와 같은 내용(이름·정규화 번호·상품·연락 시간·동의·처리방침 버전)을 다시 보내면 같은 키를 쓴다.
  - 하나라도 바뀌면 새 키를 만든다. 이전 내용으로 되돌려도 직전 시도와 다르면 새 키다.
  - 키·입력·봇 토큰은 컴포넌트 메모리에만 있다. 저장소·URL·로그·분석으로 보내지 않는다.
- **봇 토큰:** 일회용이라 보내는 순간 비운다. 접수 실패면 위젯을 reset해 새 토큰을 받고, 사업 요청 키와는 섞지 않는다. 만료·오류·토큰 없음 상태에서는 전송하지 않는다.
- **응답 처리**
  - 202만 접수 성공이다. 신규와 중복을 구분하지 않는다.
  - 성공 문구는 가입·개통 완료나 확정 연락 시간을 약속하지 않는다.
  - 그 밖의 응답은 허용 목록 코드만 고정 문구로 바꾼다. 응답 원문·HTML·예외는 화면에 반사하지 않는다.
- **꺼짐 상태**
  - 폼 꺼짐(기본) 또는 공개 사이트 키 없음(기본): Turnstile 스크립트·iframe·외부 요청을 만들지 않는다.
  - 키가 없으면 접수 요청도 보내지 않는다.

**보완(PM 6908334832)**
- **봇 확인 복구:** 만료·오류·초기 스크립트 실패·render 실패(예외·ID 미반환)가 나면 고정 오류와 "자동 입력 방지 다시 확인" 버튼을 보여준다.
  - 그려진 위젯은 SDK reset으로 다시 확인한다.
  - reset이 실패하거나 위젯이 미완료 상태면 재마운트한다. 실패한 스크립트 태그를 지운 뒤 새로 1개만 넣는다.
  - 로딩이 20초를 넘기면 오류로 처리한다. 정리된 뒤 늦게 도착한 콜백은 무시한다.
- **SDK 예외 격리:** reset·remove·render 예외는 밖으로 나가지 않는다. 폼은 결과 처리(잠금 해제·문구)를 먼저 한 뒤 새 토큰을 요청하고, 새 토큰을 받기 전에는 보내지 않는다.
- **공개 준비값:** 사이트 키나 처리방침 버전이 비거나 공백이면 위젯 외부 요청과 접수 요청이 모두 0이다.
- **결과 미확인 안내:** 응답 없음·시간 초과·해석 불가·목록 밖 코드·`INTERNAL`에는 "접수 결과를 확인하지 못했습니다"를 보여준다. 같은 내용이면 같은 키로 재시도한다. 확정된 차단(봇 확인 불가·입력 오류 등)과 구분한다.

**서버 경계**
- JSON 루트가 객체가 아니면 400 `INVALID_JSON`을 돌려준다.

## 4. 광고 지표 정의 (`src/content/adMetrics.ts`)
| 지표 | 식 | 분모 0·미수집 |
|---|---|---|
| CPM | 비용 ÷ 노출 × 1000 | null |
| CPC | 비용 ÷ 클릭 | null |
| CTR | 클릭 ÷ 노출 × 100% | null |
| CPA | 비용 ÷ 해당 단계 전환 수 | null |
| CVR | 해당 단계 전환 수 ÷ (명시한 분모: 클릭 또는 방문) × 100% | null |
| ROAS | 확인된 귀속 매출 ÷ 비용 × 100% | 매출 미확인이면 null |
| CPI | 해당 없음(앱 설치 캠페인 없음) | — |

- **집계 모델(입력에 명시):**
  - `cohort`(동일 유입 코호트): 기간 안 유입자 기준으로 귀속 창 `windowDays`(1~365일, 0일 없음) 안의 전환·매출만 센다. 단계 수는 단조 감소여야 하고, ROAS는 이 모델에서만 계산한다.
  - `occurrence`(기간 발생 집계): 기간 안에 일어난 전환 수다. 지난달 접수가 이번달 개통될 수 있어 단계 간 비교를 하지 않는다. 매출을 넣으면 거부하고 ROAS는 null이다.
- **실행 시점 검증:** 달력상 유효한 날짜(윤년 포함), 모델·유입·광고 유형·전환 단계 키 enum, 횟수는 안전한 정수 0 이상, 금액은 원 단위 정수에 상한 1조 원. 잘못된 값은 계산하지 않고 거부한다.
- **입력 필수 맥락:** 기간(Asia/Seoul), 출처, 유료/자연/직접/추천 구분, 광고 유형(검색 SA / 디스플레이 DA / 소셜), 비용의 VAT 포함 여부
- **전환 단계:** 상담 접수 → 가입 → 개통 → 정산. 단계마다 따로 세며, 뒤 단계가 앞 단계보다 크면 입력을 거부한다.
- **매출:** 실제 인정된 판매 수수료에서 환수·취소를 뺀 값이다(음수 가능). 귀속 기간 없이는 계산하지 않는다. 통신사 월요금, 고객 계약액, 개당 예상 마진은 매출이 아니다.
- **자연 검색:** 비용이 있으면 입력을 거부한다. 비용 지표와 ROAS는 null이다.
- **SA/DA와 CTA:** SA/DA는 광고 유형이고 CTA는 버튼 문안이다. 같은 비용 지표로 비교하지 않는다. 유형별로 비교하고, 클릭 → 접수 전환으로 평가한다.
- **UTM:** 운영자가 미리 등록한 비식별 캠페인 코드 조합(`src/content/utm.ts`의 `UTM_REGISTRY`, 최대 50개)과 **정확히 일치**할 때만 남기고, 미등록 값은 전부 버린다(`matchUtm`).
  - 정규식으로는 영문 이름·개인 식별 코드·주소를 판별할 수 없다(예: `john.smith`). 그래서 형식 검사로 개인정보 제거를 **보장하지 않는다.**
  - 등록부는 캠페인 단위로만 쓰고 고객·개인별 코드를 등록하지 않는다. 현재 등록부는 비어 있다(광고 미집행). URL 원문을 로그에 남기지 않는다.
- **중복 집계 금지:** 광고 클릭과 접수 전환을 같은 이벤트로 두 번 세지 않는다.
- **이번 묶음에서 켜지 않은 것:** 운영 트래커, 픽셀, 쿠키, 실제 이벤트 수집, 외부 전송, 새 DB 테이블. 관리자 지표 화면은 기존 인증 + owner 범위로만 설계한다. 공개 화면에는 매출·내부 수치를 노출하지 않는다.
- **실측 전 금지:** 목표 수치 조작, 자동 입찰 최적화, 예산 증액

## 5. 총판 확인 요청 템플릿 (작성만, 발송하지 않음)

> 사용자 지시 없이 공급처에 보내지 않는다. 비밀번호·로그인 정보·고객 정보·주민번호·신분증·계좌는 이 메시지에 넣지 않고, 회신으로도 받지 않는다.

```
[딜러 ○○○] 인터넷·TV 영업 관련 확인 요청드립니다.

1. 공식 접수 경로
   - 고객이 직접 신청할 수 있는 총판 공식 접수 주소(웹 링크·전화·채널)가 있는지,
     딜러별로 구분되는 접수 주소나 코드가 있는지 알려 주세요.
2. 딜러 유입 식별
   - 그 경로로 들어온 신청이 제 실적으로 잡히는 방식(딜러 코드, 전용 링크 등)을 알려 주세요.
   - 고객 개인정보를 제가 따로 받지 않아도 되는 방식이면 그 방식으로 하겠습니다.
3. 광고 허용 범위
   - 개인(사업자등록 없음) 딜러로 온라인 광고가 가능한 매체·표현 범위와 금지 사항(통신사 명칭·로고 사용,
     "공식" 표현, 가격·사은품 표기 등)을 서면으로 알려 주세요.
   - 광고 문안 사전 검수가 필요한지도 알려 주세요.
4. 최신 정책 전달
   - 정책표가 바뀔 때 최신본과 적용 시작일을 받는 방법을 알려 주세요(가정용·SOHO 구분).
5. 민감 자료 전달 경로
   - 가입 서류처럼 민감한 자료가 필요할 때 총판이 지정하는 안전한 전달 경로를 알려 주세요.
     카톡·문자로 신분증·주민번호·계좌를 주고받지 않으려고 합니다.

감사합니다.
```
